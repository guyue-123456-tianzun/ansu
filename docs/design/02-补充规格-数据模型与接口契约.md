# 1. 数据模型（16 张表）

## 1.1 设计原则

- 16 张表不扩：白名单/阈值/时间带放 `thresholds.yaml`；课程与题库放 classpath JSON；作答放 `learning_record.answers_json`。
- 寝室主键直接用房间号（`314`），与原文 API 示例一致；`room_no` 同值，便于展示。
- 库内时间 UTC；接口输出 `+08:00`；业务时间带按 `Asia/Shanghai`。
- 功率库内 kW（`DECIMAL(8,3)`），接口对外 W（整数）。
- 枚举用 `VARCHAR + CHECK`，保留原文取值；`night_anomaly`、`open/closed` 等按原文补齐。
- 账本只追加；状态迁移只走 Java 唯一出口。

# 2. 判定规格（SafetyEngine）

## 2.1 时间带

| 时间带 | 区间（左闭右开） | 阻性处置线 | 总功率提醒线 |
|---|---|---:|---:|
| 日间 | `[06:00, 19:00)` | 500 W | 1500 W |
| 洗漱 | `[19:00, 23:00)` | 500 W | 2000 W |
| 夜间 | `[23:00, 06:00)` | 400 W | 400 W |

- 时区 `Asia/Shanghai`；`06:00:00` 日间；`19:00:00` 洗漱；`23:00:00` 夜间。
- 夜间总功率 400W 只提醒，不分闸；夜间阻性 400W 进入处置。两者分开。

## 2.2 输入与特征

原文 `Event` 已含 `stepW/durationS`；建议加一个 `FeatureExtractor`：

```text
FeatureExtractor.extract(dormId, ts, window):
  baseline_w = median(前 10s/10min)
  steady_w   = median(当前 + 前 3 点)
  pf_avg     = mean(最近 3 点 PF)
  step_w     = steady_w - baseline_w
  duration_s = 连续 ≥ identify_w 的时长
  rise_time_s= 从 10% 到 90% 的上升时间
  device_hint= 可选（设备类）
```

- `SafetyEngine.evaluate(Event, DormState, now)` 仍是纯函数，不写库、不调 Python。
- `/api/safety/evaluate` 允许直接传 `step_w/duration_s`，用于单测与调试。

## 2.3 通道、等级与优先级

原文 `Decision` 是单个对象。建议保留单对象，但**等级取最高**：

```java
public record Decision(
    Level level,              // max(所有 reason.level)
    Channel channel,          // 最高优先级通道
    Action action,            // WARN_THEN_CUT / NOTIFY / LOCK / NONE
    List<Reason> reasons,
    int warnSeconds,
    String nextIfUnresolved,
    String explain,
    String thresholdVersion
) {}
```

优先级：`urgent 漏电/温度` > `warn 漏电/温度` > `阻性` > `总功率` > `info 漏电/温度`。

> 修原文 §5.2 的 bug：命中阻性时不能把 `level` 固定成 WARN；必须把 reasons 里的 urgent 提上来。

## 2.4 阻性五元组

1. `PF_avg ≥ 0.95`
2. `step_w ≥ 300`
3. `稳态功率 ≥ 300`（识别线）
4. `持续时间 ≥ 3s`
5. 非白名单排除、非 PFC 排除

分闸条件：`稳态功率 ≥ 当前时间带 resistive_cutoff_w`。

### PFC 排除（原文只说“设备特征排除”，以下为建议实现）

满足任一即排除阻性：

- 设备类 `desktop_pc` / `pfc_computer`；
- 上升时间 ≥ 1.0s（软启动）；
- 50% 负载时 PF < 0.92；
- 阶跃后 3s 内出现第二次 ≥100W 阶跃。

> 标记为“建议补全”，不是原文规定；答辩要讲“可解释的启发式 + 设备备案”，不要声称能识别所有电器。

## 2.5 白名单

| 设备 | 额定 | 时间 | 规则 | 说明 |
|---|---:|---|---|---|
| 饮水机 | 2000W | 全天 | 免阻性分闸；专用回路免总功率提醒 | 仍校验 `breaker_rating_w=2200W`；产品文档“非永久放行”靠回路校验落地 |
| 吹风机 | 1800W | 19:00–23:00 | 免阻性（PF 0.80 本来就不命中）；洗漱 1800<2000 放行；非洗漱 1800>1500 仅提醒 | 原文设备签名 PF 0.80 |
| PFC 电脑 | 1200W | 全天 | 免阻性分闸；总功率仍算 | 夜间 1200>400 会提醒；这是预期行为 |

> 白名单不是“永久免死”：饮水机要专用回路 + 2200W 校验；电脑夜间仍受总功率提醒。

## 2.6 漏电 / 温度

- 漏电：200/300/500mA → info/warn/urgent；去抖 5s；基线 10–50mA。
- 温度：60/70/90℃ → info/warn/urgent；去抖 10s。
- 30mA 人身保护与 300–500mA 防火监测分开讲；P0 不做真实脱扣。
- urgent 漏电/温度即使 `locked` 也要告警并通知管理员（修原文代码的 lock 早返回）。

## 2.7 总功率

- 日间 1500W、洗漱 2000W、夜间 400W；只提醒，不分闸。
- 与阻性同时命中时，`channel=RESISTIVE`，总功率作为 reason 附加；`level` 取最高。
- 回路 2200W：超过则 `urgent` 过载提示（不物理分闸）；白名单设备也要校验。

## 2.8 边界与缺数

| 场景 | 结果 |
|---|---|
| PF=0.95 / step=300 / duration=3s | 算阻性（含等于） |
| 499W / 500W（日间） | 仅提醒 / 进入处置 |
| 夜间 400W 阻性 | 进入处置 |
| 夜间 400W 非阻性 | 仅总功率提醒 |
| 06:00:00 | 日间 |
| 23:00:00 | 夜间 |
| 缺数 10s | 不判定，显示“数据延迟” |
| 锁定中 800W | 不判、不分闸、不扣分；仅记录 |
| 锁定中漏电 500mA | urgent 告警 + 通知管理员 |
| 重复事件 | 幂等键去重，只判一次 |

## 2.9 `safety/evaluate` 与 `SafetyEngine` 的关系

- `/api/safety/evaluate` 只回答“这一条事件怎么判”，不写库；写告警由 `AlertStateMachine` 完成。
- 该端点按原文保留，但限制 `manager/admin` + `demo` profile；生产建议改为内部端点。
- 单测直接调 `SafetyEngine`，不经过 HTTP。

# 3. 状态机

## 3.1 寝室状态

| 当前 | 触发 | 下一 | 动作 / 留痕 |
|---|---|---|---|
| normal | `warn_then_cut` | warned | 创建 alert(open→notified)；推送；5s 倒计时 |
| warned | 5s 内功率回落/撤除 | normal | alert `resolved(auto_removed)`；不扣分 |
| warned | 5s 未撤除 | cut_off | 模拟分闸；violation_count+1；扣分；证据包；action_log |
| cut_off | 30s 功率回落 | normal | 恢复用电；**不撤销违规/扣分**；alert `resolved(auto_recover)` |
| cut_off | 首次学习 ≥80 | normal | 恢复；credit +3；learning_record + ledger |
| cut_off | 申诉通过 | normal | 恢复；撤销扣分；alert `penalty_reverted=1` |
| cut_off | 24h 内第 3 次 | locked | lock_until=+3h；通知学生/管理员 |
| locked | 管理员解锁 | normal | 记录操作人/原因 |
| locked | 3h 超时 | normal | 记录 action_log；通知学生 |
| locked | 新功率违规 | locked | 不分闸、不扣分；仅记录 |
| locked | urgent 漏电/温度 | locked | 仍告警 + 通知管理员（安全覆盖） |

## 3.2 告警状态

| 当前 | 触发 | 下一 | 动作 |
|---|---|---|---|
| open | 创建 | notified | 写 notification；`notified_at` |
| notified | 学生打开 | student_responded | `responded_at`；action_log |
| notified | 5s 内撤除 / 自动恢复 | resolved | 恢复；不扣分或按规则 |
| student_responded | 已撤除 | resolved | 恢复 |
| student_responded | 首次学习通过 | resolved | 恢复 + 信用 +3 |
| student_responded | 提交申诉 | reviewing | 创建 appeal；SLA |
| student_responded | **第 2 次学习通过** | **reviewing** | 不自动恢复；转宿管复核（修 X03） |
| reviewing | 通过 | resolved | 恢复 + 撤销扣分 + 通知 |
| reviewing | 驳回 | resolved | 写理由 + 通知 + 学习/锁定 |
| resolved | 24h 归档 | closed | `closed_at` |
| notified | 10 分钟无动作且功率正常 | resolved | `resolved(auto_timeout)` |
| student_responded | 24h 无动作 | closed | `closed(timeout)` |

## 3.3 申诉状态

| 当前 | 触发 | 下一 | 守卫/副作用 |
|---|---|---|---|
| — | 提交 | submitted | 证据包；deadline=+24h（夜间取次日10:00较晚者）；original_penalty |
| submitted | 宿管接单 | reviewing | 记录 reviewer_id |
| submitted | 学生撤回 | withdrawn | 停止 SLA |
| reviewing | 通过 | approved | 恢复；撤销扣分；`penalty_reverted=1`；通知 |
| reviewing | 驳回 | rejected | 必须 ≥10 字理由；通知；进入学习/锁定 |
| reviewing | 超时 | reviewing | `escalated=1`；通知管理员；不自动裁决 |
| approved/rejected | — | 终态 | 不可再改；纠正走管理员调整 |

**路由**：

- 第 1 次：学习恢复 / 申诉 / 等宿管，**三选一；申诉与学习不能同时**（原文开发 §5.5）。
- 第 2 次：学习 + 宿管复核，不自动恢复。
- 第 3 次：仅 `misjudge` / `device_fault`；`special` 返回 42201；锁定 3h。
- 锁定中：仅管理员解锁；学习不能绕过。
- 超时：升级管理员，不自动通过/驳回。

## 3.4 信用分

| 事件 | delta | 限制 |
|---|---:|---|
| 基础分 | 100 | 每宿舍 |
| 第 1/2/≥3 次违规（滚动 24h） | -8 / -12 / -20 | 只计未回滚违规 |
| 完成学习 | +3 | 每课每自然月一次；每月最多 +6 |
| 30 天无违规 | +2 | **每月结算一次，检查滚动 30 天**；幂等 `(dorm, yyyy-MM)` |
| 申诉通过 | 反冲原扣分 | 不额外加分 |
| 有效报修 | +1 | P1；每月最多 +2 |
| 区间 | 0–120 | 越界夹紧 |

- 账本只追加；`appeal_revert` 反冲 `original_penalty`；`alert.penalty_reverted=1`。
- 未来 `seq24h` 只统计未回滚违规。
- 并发：`SELECT ... FOR UPDATE` 锁 `dorm` 行；唯一键防重复。
- 第 1 次申诉与学习二选一，避免“又回滚又加分”的套利。

# 7. 通知 outbox

- 写通知与状态迁移同一事务；`status='pending'`。
- J8 每 30 秒扫描 `pending && next_retry_at<=now`；P0 只做站内“发送”（标记 `sent`）。
- 失败：`retry_count++`，`next_retry_at = now + 2^retry_count * 30s`，最多 3 次。
- 已读：`PATCH /api/notifications/{id}`；重复调用幂等；未读数 `read_at IS NULL`。
- 幂等键：`notify:{user_id}:{ref_type}:{ref_id}:{type}`。

# 8. 演示 run 与重置

## 8.1 run 生命周期

```text
created → active → archived
```

- `demo_run.id` 为 16 位字符串（如 `run_7f3a91c2`）。
- 同一时刻只有一个 `active`；`dorm.active_run_id` 同步。
- `switch`：旧 run → `archived`；清理 run 作用域；新 run → `active`。
- 固定 seed：`20261110`；同场景 + 同 seed → 同曲线/同告警/同数字。
- 大屏/学生端/简报/问答都带 `run_id`；缺省取 active。

## 8.2 场景

| 场景 | 初始 | 注入 | 预期 |
|---|---|---|---|
| normal | 20 寝 normal，314 基线 32W | 无 | 无告警 |
| violation | 同上 | 23:10 热得快 800W，8s | 3s 橙、5s 红、分闸、学生告警 |
| appeal | violation 后 | 学生提交设备故障申诉 | 宿管待办、SLA |
| night | 夜间基线 | 314 400W 阻性 | 按夜间 400W 处置 |

## 8.3 重置范围

`POST /api/demo/reset`（admin + demo profile + 二次确认）：

1. 删除 run 作用域：`load_record`（`demo_run_id` 非空）、`alert_log`、`appeal`、`action_log`、`learning_record`、`credit_ledger`、`notification`、`briefing`、`qa_log`、`demo_run`。
2. 重置 `dorm`：status=normal、violation_count=0、last_violation_at=NULL、lock_until=NULL、credit_score=100、active_alert_id=NULL、active_run_id=NULL。
3. 保留：`building`、`dorm` 主数据、`user_account`、`threshold_version`。
4. 重新生成/保留 `source='seed'` 基线。
5. 返回各表删除行数；目标 <30s。

> 场景切换只清 run 作用域，不清账号/阈值；全量重置用 `seed_demo --reset --yes`。

## 8.4 数字一致性

- 大屏、学生端、简报、问答读同一 `run_id`。
- 简报的违规/申诉/学习数字来自同一 run 聚合。
- 彩排前跑 `smoke.sh` 对账。

## 9.7 护栏

| 护栏 | 实现 |
|---|---|
| 不发明数字 | 输出数字必须在 payload 数字集合中 |
| 不发明规则 | 必须返回 `rule_ref`，且属于当前 `threshold_version` |
| 不越权 | Python 只接收 Java 传入的本宿舍数据 |
| 不静默失败 | 异常/超时返回模板，`gen_by='tmpl'`；HTTP 200 |
| 不无限等待 | 连接 500ms；读 8s；熔断 30s |
| 长度/语气 | 每段 40–300 字；禁止“保证/一定/绝对/必然” |
| 格式 | JSON schema 校验；缺字段 → 模板 |

## 9.9 模板兜底

### 阻性

- what：`{time} 检测到功率从 {baseline_w}W 阶跃到 {steady_w}W，持续 {duration_s} 秒，PF {pf}。`
- why：`PF ≥ 0.95；阶跃 ≥ 300W；持续 ≥ 3s；非白名单。依据平台规则 {rule_ref}（{threshold_version}），阈值口径来自学校宿舍用电管理规定。`
- action：`拔掉设备 30 秒可恢复；如果是误判可申诉；首次违规可完成安全学习提前恢复。`

> 不要编造“《宿舍安全用电规范》第 4.2 条”这类具体条款号；只写“校规口径/平台规则”。

### 总功率

- what：`{time} 宿舍总功率达到 {steady_w}W，超过当前时段提醒线 {threshold_w}W。`
- why：`当前时段总功率超限；本次仅提醒，不直接分闸。`
- action：`错峰使用大功率电器；检查是否有设备异常发热；必要时报修。`

### 漏电/温度

- what：`{time} 检测到剩余电流 {leakage_ma}mA / 温度 {temp_c}℃。`
- why：`超过 {level} 阈值；已通知管理员。`
- action：`停止使用相关插座；不要自行拆修；等待管理员/维修处理。`

{actions_list}

## 10.4 状态与异常

| 状态 | 界面 |
|---|---|
| 空数据 | “暂无告警” + 最近巡检 |
| 数据延迟 | 黄色角标 + 最后更新时间 |
| AI 降级 | “模板模式”徽标；`meta.degraded` |
| 通知失败 | “未触达” + 重发 |
| 申诉超时 | 红色 SLA + 已升级 |
| 事件流中断 | 红色横幅 + 重置 run |
| 403 | “仅可查看本宿舍” |
| 锁定 | 灰色 + 解锁时间/管理员处理 |

- 用“疑似违规电器/需要确认”，不用“偷电/违规分子”。
- 不显示他人宿舍、个人排名、姓名/学号。
- 不承诺“一定恢复/绝对安全”。
- 降级明示“模板模式”。
