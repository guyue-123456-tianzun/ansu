### 1.2 单人 26 天的可行性裁决

按原文原样执行（28 个业务 API、16 张表、12 个页面、6 类角色、3 分钟微课、UCI 数据导入、5 个 Python 端点、三端联调、TC01–TC30 全过），**1 人从零在 25 个开发日内完成并达到稳定演示质量，不可行**。原文自己按 **1.5 人** 设计（产品 §3.4）；1 人低于原假设。主要不是“写不完”，而是“写完了没有时间调稳定、对数字、做降级、练答辩”。

本方案建议把目标改为 **“Demo-P0 垂直切片”**：

- **28 个业务端点（原文 26 P0 + 2 P1）+ 2 个基础设施/动作端点**（演示身份切换、已撤除）
- 16 张表（按原字段补齐；阈值/白名单走 `thresholds.yaml`，课程/题库走 classpath JSON，不扩表）
- 6 个核心页面（大屏、告警工作台、申诉工作台、简报中心、宿舍卡、告警详情）
- 3 个演示角色（学生、宿管、管理员）
- **5 个 Python 端点**（explain、qa、briefing、simulate、health；qa 可薄）
- **UCI 基线（D2 前数据就绪）+ 1 Hz 演示突发；否则合成基线并明示 `source=seed`**
- 学习环节三选一：申诉版 / 速通版 / 预完成版（见 `02` §6.4）

**判断：按 8–10 小时/天、AI 辅助编码、严格执行砍范围，交付概率为中等偏高；若坚持原文全量 P0，交付概率低。** 这不是降低标准，而是把标准集中到“90 秒主链路 + 数字一致 + 可降级 + 讲得清边界”上。

### 1.3 必须先解决的 7 件事

1. **3 秒指标与轮询方案冲突**：2 秒 Java 轮询 + 3 秒学生轮询，最坏 5 秒，P0 验收必然失败。
2. **夜间总功率 400W 在原文内部冲突**：判定表写了“夜间 ≥400W 提醒”，但 `thresholds.yaml` 与 `SafetyEngine` 代码没有 `night_limit_w`；需补上。
3. **第 2 次学习后的状态冲突**：原文一处写 `resolved`，一处写“转宿管复核”，状态机会分叉。
4. **16 张表的真实缺口不是“装不下”**：原字段基本够；缺的是 outbox 字段、课程正文/题库、作答/证书、白名单配置。用 YAML + JSON + 字段补齐。
5. **90 秒剧本塞不下 3 分钟微课 + 5 题测验**：原文 55–70s 只有 15 秒；必须改申诉版，或明示“速通/预完成”。
6. **28 个业务端点不含登录/已撤除**：原文用演示令牌；需补 2 个基础设施/动作端点，或接受“无登录/仅自动恢复”的演示缺陷。
7. **锁定中的安全覆盖是代码 bug**：原文 `SafetyEngine` 在 `locked` 时直接返回，连 urgent 漏电/温度也吞掉；必须改为“普通功率不判，urgent 仍告警”。

### 2.2 可以直接复用的强项

- **产品边界**：不碰强电、不装摄像头、信用分到宿舍不到个人、不挂钩评优。这四条能挡住答辩中大部分伦理追问。
- **六步闭环**：识别 → 提醒 → 解释 → 处置 → 学习 → 复盘，是演示的天然脚本。
- **三层状态机**：寝室、告警、申诉分开，是比“一个 status 字段”更专业的表达。
- **降级矩阵**：Python 挂、LLM 超时、断网、学生端打不开、数字对不上，都有话术。
- **术语表**：三个最容易说错的词（断电/模拟分闸、AI 判违规/规则判定、个人信用/宿舍信用）非常有用。
- **演示故障兜底**：先降级不 debug、先保主链路、诚实说边界，是现场救命的三条原则。

## 八、审阅结论

这份文档已经把“为什么做、给谁做、怎么讲”讲得很清楚，缺的是“怎么把它做成”。对 1 人 26 天的现实约束，正确的策略不是把 12 个页面都做一遍，而是：

> **用 6 个页面、28 个业务端点 + 2 个基础设施端点、16 张表，把 90 秒主链路做成一条能反复跑、数字对得上、断网也不慌的垂直切片；其余全部延期。**

只要这条切片稳定，答辩就能赢；如果切片不稳，功能再多也会在现场崩掉。
